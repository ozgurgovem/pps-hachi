# DECISIONS.md

One line per architectural decision: **date · decision · reason**. Append, never rewrite.
When we change our minds, add a new row that supersedes the old one and mark the old one
`SUPERSEDED by D-NN`. This file is the record an auditor — or a future session — reads to
find out *why*, not *what*.

Status values: `LOCKED` (do not relitigate without asking) · `OPEN` (decided but revisitable)
· `PENDING` (raised, not yet decided) · `SUPERSEDED`.

### Phase 2 persistence — plan reviewed by an independent Opus pass before any code, 2026-08-02

The schema/migration/persistence design below was drafted, then sent to an independent architectural review (opus model, no visibility into the drafting) before implementation, because every phase from here to 12 reads and writes through this same `.ppsx` format — a mistake here compounds. The review found one issue that would have silently destroyed user data (D-51) and several structural gaps the draft plan hadn't addressed. Four were genuine product decisions, not engineering calls, and went to Barış rather than being decided unilaterally (D-58 through D-61), per `CLAUDE.md`'s "ask me, do not silently invent scope."

| D-51 | 2026-08-02 | **`ProjectModel` Zod schemas are loose (`.passthrough()`/`.loose()`), never stripping unknown keys. Any additive schema change ships with a `schemaVersion` bump.** | Zod object schemas strip unrecognised keys by default. Since "validate the parsed result, then save that" was the planned open/save flow, a field added by a newer build is silently deleted the moment an older build opens and re-saves the file — no error, no warning. This is the exact failure `docs/01_ORIENTATION_REVIEW.md` §1.5 already flagged for `Entry.payload`; it turns out to apply to the whole model, and the validation step itself is what causes it. Caught by the Opus review before any schema was written. | LOCKED |
| D-52 | 2026-08-02 | **`Entry.payload` is `z.unknown()` at the `ProjectModel` level. Project load never inspects or validates it — that is a method-plugin concern at edit/render time. Closes the structural half of P-05; the UI half (read-only placeholder for an unknown `methodId`) moves to Phase 3.** | P-05 was tagged "Blocking: Phase 2" and the original Phase 2 draft plan didn't address it — at Phase 2 the method registry is empty, so validating payload shape at load time would refuse every project with any entry at all. Splitting it lets Phase 2 guarantee "an unknown `methodId` round-trips untouched" (a ~15-line fixture test) without needing the placeholder-card UI that only makes sense once the workspace exists. | LOCKED |
| D-53 | 2026-08-02 | **`StepState.readiness` is never persisted.** `ReadinessResult` is a derived selector return type living in `src/domain/readiness/`, not a field in the `src/domain/model/` schema. | `SPEC.md` §4.2 sketches `readiness` inside `StepState` but marks it "derived, not stored" in the same line — transcribing the sketch literally would persist it anyway. A stored readiness goes stale the moment a gate rule changes, and the file then disagrees with the app about whether a step passes, on a document whose whole purpose is to be defensible in an IATF audit. Already flagged in `docs/01_ORIENTATION_REVIEW.md` §1.10; carried forward here so it can't be missed again. | LOCKED |
| D-54 | 2026-08-02 | **`manifest.json` is the routing header — read first, structurally validated in Rust, decides migrate / refuse / open-read-only before `project.json` is touched. `project.json` is authoritative for content. A mismatch between the two (e.g. differing `id` or `schemaVersion`) is reported as a corrupt file, never silently reconciled.** | `SPEC.md` §4.1 and §4.2 both list `id` and `schemaVersion`, with no stated precedence — duplicated state with no precedence rule is a bug waiting for a hand-edited or partially-written file. ### Post-implementation security review — independent Opus pass on `archive.rs` + `atomic.rs`, 2026-08-02

Requested after Phase 2 shipped, scoped to the two files handling untrusted external input (a `.ppsx` arriving by email, per D-06) and the atomic-write primitive. | D-67 | 2026-08-02 | **`read_ppsx` never trusts `entry.size()` (the zip's declared uncompressed size) for allocation or as the cap enforcement mechanism.** `read_capped` bounds actual bytes read via `.take(budget + 1)`, where `budget` is the tighter of the per-entry and remaining-total caps; the declared size is not consulted at all.
